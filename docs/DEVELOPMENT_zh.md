## 1. 项目背景与目标

开发一款 Android 应用，调用手机摄像头**拍摄一张桌面散放的整组麻将牌照片（单张照片一次识别）**，纯端侧离线完成：

1. **精准计数**：识别图像中麻将牌总数量，**花色朝下（背面朝上）的牌也计入总数**，与期望张数（默认 108）比对。
2. **花色与点数识别**：识别每张正面朝上牌的牌面（仅 万 / 筒 / 条，各 1–9，共 27 种，无字牌）。
3. **缺牌反馈**：告知总数量、各花色分布、缺少的整门花色及缺牌明细（如"五万应有 4 张，实到 2 张"）。
4. **智能提示**：存在背面朝上的牌、总数正确但缺花色/缺牌时，提示用户"缺少的牌可能在朝下的牌中，请翻开检查"。
5. **历史记录**：每次识别结果自动保存，可回看、删除。

**核心原则（v0.4）**：一切以**识别精度**为先；识别时间与模型体积均为精度让路（见 2.2）。

## 2. 需求分析

### 2.1 功能需求

| 编号 | 需求 | 说明 |
|------|------|------|
| FR-1 | 相机拍摄 | 应用内高分辨率拍照（CameraX）；**相册选图（已实现，转正）**，两者共用同一识别流程 |
| FR-2 | 麻将检测 | 定位桌面散放场景中的每一张牌（含部分遮挡），区分正面/背面 |
| FR-3 | 数量统计 | 总数 = 正面 + 背面，与期望张数（默认 108）比对 |
| FR-4 | 牌面识别 | 27 种牌（万/筒/条 × 1–9）+ 1 种牌背 = 28 类；**字牌/花牌方向已终止** |
| FR-5 | 缺牌分析 | 每种牌应有 4 张，逐种核对；同时给出整门花色是否缺失；**N < 108 时报告追加"部分清点"说明行**（见 3.4） |
| FR-6 | 智能提示 | 见 3.3 业务规则 |
| FR-7 | 结果展示 | 原图叠加标注（框+中文牌名），下方文字报告 |
| FR-8 | 期望张数设置 | 默认 108，可改（1–999，兼容部分清点场景） |
| FR-9 | 历史记录 | **标准版**：识别成功自动保存（时间、期望/实际张数、花色分布、报告全文、结果缩略图）；列表 → 详情回看；单条删除 + 清空全部（带确认）；保留最近 **50 条**，超出自动清理最旧；存储于应用私有目录，不需任何权限 |

### 2.2 非功能需求（v0.4 重订）

- **离线端侧**：TFLite 本地推理，无任何网络依赖。
- **速度**：**不设硬性上限**（v0.3 的 ≤5 秒、此前的 1–2 分钟均废除）。实测值记录于文档 §10 供参考。允许用时间换精度。
- **模型体积**：**≤ 500MB**（v0.4 起放宽；现行 1280 双模型 45MB，下一代 1920 双模型预计 ~80MB，见 4.1-C）。
- **准确率**：见 2.3。
- **系统**：Android 8.0（API 26）及以上；**targetSdk 36**（对齐 Android 16 部署实机）。
- **交付形态**：debug APK 自用；不做应用图标、release 签名、混淆。

### 2.3 准确率验收方式（v0.4 重订）

- **验收口径 = 实拍回归集 + 用户主观认可**：
  - 用户拍摄 **5–10 张**典型场景照片（清单见附录 A），拍照时顺手记录每张**真实张数**作为计数基准（零标注成本）；
  - 每次模型/管线改动后跑回归集，对比识别总数与报告；
  - 是否"算达标"以**用户看过结果主观认可**为准，不以数字门槛卡验收。
- **长期方向**（不卡验收，持续迭代）：计数准确率 ≥98%、牌面识别 ≥95%。
- **升级硬性验收的两步路径**（将来如需）：
  1. 第一步：扩大回归集至 20–50 张并坚持记录真实总数（仍零标注成本）→ 可客观度量计数准确率；
  2. 第二步：对关键照片逐张标注（YOLO 格式 `类别 cx cy w h`，0–1 归一化；先用现有模型预标注、人工只改错框，每张约 1–2 分钟）→ 可度量牌面准确率。

## 3. 业务规则定义

### 3.1 花色体系（已确认）

- 仅 **万子、筒子、条子** 三门，各 1–9，共 27 种牌；每种 4 张，全组 **108 张**。
- 无字牌、无花牌。
- 检测类别 = 27 种牌 + 1 种牌背（`back`）= **28 类**。

### 3.2 缺牌判定

- 统计正面牌中每种牌的数量，与应有数量 4 比对：
  - 实到 < 4 → 缺牌（列出明细：牌名 × 缺几张）
  - 实到 > 4 → 异常多出（混入其他组的牌，同样报告）
- 某花色（万/筒/条）所有 9 种牌实到均为 0 → 判定**整门花色缺失**，单独醒目提示。

### 3.3 智能提示逻辑（核心规则，v0.4 原样保留）

```
输入：检测结果（每张牌：位置 + 类别 + 置信度）、期望张数 N（默认 108）

total    = 全部检测到的牌数（含背面牌）
faceDown = 背面牌列表
shortage = 缺牌明细（每种牌 应有4 - 实到 > 0 的项）

1. 报告总数：
   - total == N → "数量正确，共 108 张"
   - total <  N → "数量不足：检测到 total 张，缺 N-total 张"
   - total >  N → "数量超出：检测到 total 张，多 total-N 张"

2. 报告花色分布与缺牌明细 / 整门缺失

3. 智能提示：
   若 faceDown 非空 且 total == N 且 (存在缺牌或整门缺失)：
       → "检测到 X 张牌花色朝下。缺少的【五万×2…】可能就在这 X 张
          朝下的牌中，请翻开核对。"
   若 faceDown 非空 且 total != N：
       → "检测到 X 张牌花色朝下，请翻开后再确认数量与花色。"

4. 低置信度提示：
   存在置信度 < 0.55 的检测 → "X 张牌识别置信度较低，建议换个角度重拍确认"
```

### 3.4 部分清点说明（v0.4 新增）

- 缺牌明细**始终**按"每种应有 4 张"的整副口径计算（保持报告完整、逻辑简单）。
- 当期望张数 **N < 108**（用户只拍了一部分牌）时，报告额外追加一行说明：
  `当前为部分清点（期望 N 张），缺牌明细按整副 108 张口径计算`
- 整门缺失判定同口径（某门 9 种全为 0 才报，不因部分清点误报）。

## 4. 技术方案

### 4.1 识别方案（端侧深度学习）

**4.1-A 当前部署（v0.4 时点，保持可用）**

- 三模型集成（各 YOLOv8n，int8 TFLite，输入 640×640，共 9.6MB）：
  | 模型 | 来源 | 职责 |
  |---|---|---|
  | `mahjong_28cls_int8.tflite` | runs/mj-v2 | 正面牌（28 类） |
  | `mahjong_28cls_back_int8.tflite` | runs/mj-user-v1 | 整齐蓝/绿牌背 |
  | `mahjong_28cls_back_scattered_int8.tflite` | runs/mj-user-v3 | 散放牌背辅助（conf 0.20 + 框内蓝/绿像素 ≥18% 才采信） |
- 大图切片检测：4000×3000 原图 → 640×640 重叠 25% 切片 → 逐块推理 → 坐标映射 → 全局按类别 NMS。
- 推理后端：CPU/XNNPACK（准确率优先，GPU 半精度会丢低置信目标，GPU Delegate 保留为回退）。

**4.1-B 下一代模型（v0.4 选型确认，工程交付后启动训练）**

- 原则：**精度至上**，体积 ≤100MB、时间不设限。
- 规格：
  | 模型 | 规格 | int8 体积 | 说明 |
  |---|---|---|---|
  | 正面 | **YOLO11l @1280** | ~26MB | 牌面为细粒度分类，大模型收益主要在 1–9 字符辨识 |
  | 牌背 ×2 | **YOLO11m @1280** | 各 ~21MB | 牌背是简单任务，11m 已富余，不选 11l |
  | 合计 | | **~68MB** | ≤100MB 红线内 |
- 训练策略：**640 预训（COCO 预训练权重迁移）→ 1280 短程微调**，本机 MPS；避免把 GB 级数据传 Colab。
- 切片升级：640 → 1280（每块看到更多完整牌、边界切半更少；`ImageSlicer`、合成数据生成、推理管线参数同步改）。
- **数据侧优化优先于架构**：用户实拍持续入库、按回归集错例定向补数据，比换更大模型收益更大。
- YOLO11n 保留为速度优先备选；v9/v10/v12/RT-DETR 不采用（TFLite int8/手机 CPU 成熟度差，免 NMS 优势在切片管线下用不上）。

**4.1-C 下一代 2.0（1920 轮，2026-08-30 决策，训练交付给 GPU 盒子）**

- **分工**：训练与 TFLite 导出全部在 GPU 盒子（优先 L40，其次 DGX Spark）；Mac 负责整合（assets/切片参数/回归）+ APK；用户负责真机验证。
- **体积预算 ≤500MB**，实际选型约 80MB——YOLO11x 已是家族上限（int8 约 57MB），RT-DETR 等更大架构手机端 TFLite int8 路径不成熟、CPU 推理分钟级，不采用。
- **规格**：
  | 模型 | 规格 | 说明 |
  |---|---|---|
  | 正面 | **YOLO11x @1920**（COCO 11x 全新 640 预训 → 1920 微调） | 11l→11x 无法跨架构迁移权重，需重新预训；11x int8 ≈57MB |
  | 牌背 | **YOLO11m @1920 微调**（直接从现成 mj-back-11m-640 best 起步，免二次预训） | 牌背任务简单，11m 足够 |
- **切片**：部署与训练统一切 **1920**（640 整数倍；4000×3000 原图 6 块切片）；合成数据 `generate.py --canvas 1920`，用户照片切片同步 1920。
- **手机端推理预期**：11x@1920 单块 CPU 推理约 6–15 秒 ×6 块，总耗时 1–2 分钟（无硬限，真机实测后回填）。
- 训练完成后传回：各 run 的 weights/ + results.csv + args.yaml（若盒子已导出 tflite 则一并），Mac 侧整合流程同 §10.5。

### 4.2 技术栈

- Kotlin + Jetpack Compose + CameraX
- TensorFlow Lite（int8，CPU/XNNPACK 优先，GPU Delegate 回退）
- 训练侧：Python + Ultralytics（Apple Silicon MPS）
- 历史记录：org.json 序列化 + 应用私有文件存储（零新依赖）

### 4.3 数据集与模型训练

1. **公开数据集**：覆盖 27 种牌面 + 牌背，多牌具样式（沿用 mj-v2 等既有数据）。
2. **合成数据**：裁剪牌面/牌背特写，随机旋转/缩放/透视 + 多种桌面背景 + 散落/重叠/阴影（`training/synth/generate.py`；1280 升级时重生成）。
3. **用户实拍**：牌背网格图（4 张 12×10）已入库微调出 mj-user-v1/v3；后续实拍按回归集错例持续入库。
4. **指标**：mAP@50 ≥ 0.95；单独考核 `back` 类召回率（直接影响计数）。
5. **已知局限**：验证集指标 ≠ 用户真机计数准确率；以 2.3 回归集为准。

### 4.4 系统架构

```
┌────────────────────────────────────────────┐
│ UI 层 (Compose)：拍摄页 / 结果页 / 历史页     │
├────────────────────────────────────────────┤
│ 历史层：HistoryStore（JSON + 缩略图文件）     │
├────────────────────────────────────────────┤
│ 领域层 (纯 Kotlin，可单测)                   │
│  TileAnalyzer：计数/缺牌/智能提示/文字报告    │
├────────────────────────────────────────────┤
│ ML 层                                       │
│  AnalysisPipeline：切片→推理→映射→全局NMS    │
│  FaceAndBackEnsemble：三模型集成             │
│  TileDetector：TFLite 推理   ImageSlicer     │
├────────────────────────────────────────────┤
│ 相机层：CameraX 高分辨率拍照 + EXIF 解码      │
└────────────────────────────────────────────┘
```

核心流程：拍照/选图 → EXIF 校正 → 切片 → 三模型推理 → 全局 NMS → TileAnalyzer 规则报告 → 保存历史 → 结果页（标注图 + 文字报告）

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 108 张密集小目标漏检 | 计数不准 | 高分辨率拍摄 + 重叠切片（未来 1280）+ 全局 NMS；引导均匀铺开 |
| 牌相互重叠 | 漏检/误检 | 合成数据含重叠样本；重叠严重时低置信度提示重拍 |
| 公开数据与用户牌具域差 | 牌面/牌背精度下降 | 实拍持续入库 + 多样式合成 + 强增强；回归集暴露错例后定向补数据 |
| 牌背纹理因牌具而异 | back 漏检 → 计数错误 | 用户牌背数据微调 + 散放辅助模型 + back 召回单独考核 |
| 强光/反光/阴影 | 误检漏检 | 数据增强 + 拍摄引导 |
| 大模型训练周期长（11l@1280） | 迭代变慢 | 640 预训迁移 + 1280 短程微调；接受（精度至上） |
| targetSdk 36 在旧 AGP 上的兼容性 | 构建受阻 | suppressUnsupportedCompileSdk 压制告警；必要时升 AGP |

### 10.6 牌背"套框重复"修复（2026-08-31）

- **现象**：真机牌背测试检出 126–127 张且标注图有明显重复框。取证（历史缩略图放大）确认：切片接缝处模型对同一张牌给出"一紧一松"两个框，**IoU 仅 0.2–0.3 但包含率接近 1**，IoU NMS（0.3）无法去除。
- **修复**：`Nms` 新增包含率去重（intersection / min(area) > 0.6 视为重复，置信度低者剔除）；`AnalysisPipeline` 正/背全局 NMS 均启用 0.6 包含率阈值；相邻真实牌互相覆盖 <10%，不受影响。
- **桌面验证**：4 张牌背网格 125–127 → **120–121**（四张 ±1 一致），预览图重复框全部消失；正面照片计数不变。
- **使用说明**：报告的"多 N 张"是拿期望张数（默认 108）比较的——拍约 120 张的网格时应把拍摄页"期望张数"改为实际值，否则必然显示超出。
- 另：修复期间发现并解决了 LaunchedEffect 重启丢结果的 bug（见上），并在 App 内新增 `--es debug_image` 调试入口用于脚本化真机回归。
- **量化精度结论（真机实证）**：双 int8 部署时牌背模型（11m）框回归明显劣化（套框/松框 mess），而正面模型（11l）int8 无损。为此做过双 FP32 验证（框质量与桌面完全一致、牌背 121 张），但正面 11l FP32 在开发机 CPU 上超 9 分钟不可接受。**最终采用混合精度：正面 int8 + 牌背 FP32**（assets 102MB），真机验证正面 112 张（与桌面 ±2）、牌背 121 张（与桌面一致），MI CC 9 单张约 2 分 56 秒（Android 16 部署机预期显著更快）。
